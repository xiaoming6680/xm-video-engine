# 新项目流程

从一首歌到发布。**先粗后细，每一步只定一件事，定了就锁住**。命令都在项目根目录运行，除非写了 `cd app`。

> 为什么这样排（2026-10-07 复盘 HER、Clarity、Falling_Again、Still_Shining、暗叫、AI的上限等项目）：以前每一轮都拿完整成片来评审，而单调、太碎、节奏、运镜看不懂这类问题只有动起来、看整体才看得出——看出来时每个镜头都已精做完，一改就是推翻。方向在文字和静帧上确认，失败却出在运动和节奏上；唯一没推翻的《什么是AGI》先做了三段带声音的真实代码样片。所以：**动态的东西尽早给用户看，粗的时候就看整体，精做只在锁定之后。**

| 步 | 做什么 | 给用户看 | 锁定什么 |
|---|---|---|---|
| 0 | 规格 | 平台、画幅、截取范围 | 规格（之后改 = 重开项目） |
| 1 | 音频数据 + 节拍校验片 | `render.ts beatcheck` | 小节、段落、drop 位置 |
| 2 | 方向样片 | 2–3 个方向，各 10–15 秒带声音的真实代码样片 | 方向、技术路线 |
| 3 | 全片粗分镜 | `render.ts animatic`：整首歌，色块占位，真运镜、真切点、真字幕时机 | 结构（每小节放什么、景别、节奏、起伏） |
| 4 | 关键镜头打样 | 2–3 个镜头做到成片质量 | 画面标准（之后“质感”都以这几帧为准） |
| 5 | 分段精做 | 每段单独出短片 | 只改这一段 |
| 6 | 整片合成、验收、发布 | 成片 | — |

规矩：

- **第 2、3 步一定停下来给用户看**（各十几分钟），即使用户说“先做完”——这时说明这两步是为了少推翻，再听用户的决定
- **锁定写进 TREATMENT 的「已锁定」**：之后的意见如果动到锁定项，先说清是重开、会影响哪些部分，用户同意再改
- **反馈写进 TREATMENT 的「反馈记录」并标范围**（这一镜 / 这一段 / 全片）。意见模糊（“力度不足”“不够高级”）时先问清楚，或只在那一处做两个版本让用户挑；不自己把一句意见放大成全片统一改动
- **每轮评审是一次 git 提交**（`git tag v3-animatic` 之类当基准），不整份复制版本目录；退回某段就从提交里取
- 同一首歌只开一条线；想试别的方向就在第 2 步多做一个样片，不另开项目

## 0. 规格

```bash
python <引擎目录>/tools/new_project.py <新项目目录> [--vertical]
cd <新项目目录>/app && bun install
```

新项目里会生成一份 `CLAUDE.md`（流程和质量下限，指回基础引擎的文档），参考视频放 `refs/`（`.gitignore` 已让它们不进仓库）。

改 `app/src/config.ts`：画布尺寸（横 1920×1080 / 竖 1080×1920）、视频起止（截取片段）、输出文件名；母带很响时填 `AUDIO_FILTER`。平台（抖音 / B 站）、画幅、时长写进 TREATMENT「四、规格」，**锁定**。

## 1. 音频数据 + 节拍校验片

1. 歌放成 `audio/song.wav`（44.1 kHz；剪辑版先剪好再放）
2. 内嵌歌词**直接写文件，不打印**：`ffprobe -v quiet -show_entries format_tags=LYRICS -of default=nw=1:nk=1 歌.flac > data/lyrics.src.lrc`
3. 分离：`python analysis/separate.py vocals`，`python analysis/separate.py demucs`
4. 节拍和包络：先 `python analysis/analyze.py` 出拍网格；`python analysis/structure.py` 出段落草稿（SongFormer，打印吸附到小节线的 `SECTION_BARS` 草稿；接商单的片子不用，见 `docs/模型选型.md`）；再 `python analysis/analyze.py --bars` 看每小节的表，对照草稿按听感填 `SECTION_BARS`，最后 `python analysis/analyze.py`。草稿只是起点，段落以节拍校验片锁定的为准
5. 歌词对齐：`python analysis/ctc_align.py`（长歌用 `CTC_T0` / `CTC_T1` 分段）；合成人声再跑 `analysis/snap_words.py`
6. 声音事件：`python analysis/events.py --bars`，阈值不准就调。找人声切片时要避开唱词，所以排在歌词对齐之后；歌词时间改过就重跑
7. 检查：`cd app && bun scripts/render.ts info`（只列行号、时间、字数）
8. **节拍校验片**：`cd app && bun scripts/render.ts beatcheck` → `out/check/beatcheck.mp4`。黑底配原曲：大号小节号、四拍方块、整首歌的段落条、鼓点和事件的卷帘、包络、歌词行（只显示行号）。发给用户听：数字是不是跳在强拍上、段落名对不对、drop 在哪个小节。**锁定**小节和段落（Falling_Again 的 drop 判早 1.55 秒、Clarity 切点早一小节，都是看成片才发现的）

纯音乐不需要 2、5 两步，引擎没有歌词文件也能跑。

Python 依赖：numpy、scipy、librosa、soundfile、torch、torchaudio、audio-separator、opencv-python、Pillow、fonttools。

## 2. 方向样片

- TREATMENT（从模板来）先写零到二节：歌曲档案、方向、一句话。多个候选写进 `docs/方向提案.md`
- 每个方向做一段 **10–15 秒、带声音、用真实绘制代码** 的样片，挑最能说明方向的那段（通常是 drop 或副歌开头）。草稿质量即可（`render.ts video --from a --to b --samples 1`），但运动、节奏、技术路线必须是真的：要用 3D 就真用 3D，要角色动就真让它动
- 静帧、概念图（Codex 生图）可以一起给，但**不能只给静帧**：静帧看不出“像 PPT”“单调”“动作假”
- 用户选定后**锁定**方向和技术路线，写进 TREATMENT「一、方向」和「已锁定」
- 想借参考片：先问清借什么（构图？节奏？镜头感？），写进「三、对标作品」，免得把“要镜头感”理解成“要那种画风”
- 画风和模块：查 `docs/模块目录.md`、`docs/复刻配方.md`；第三方笔刷、角色骨骼等在 `third_party/`
- 有参考片时，方向样片那一段就按 `docs/复刻配方.md` 第五节对照参考，先做到**单帧像 + 连贯 + 运动量接近**，再换成自己的内容；只做到“效果有了”的样片会被推翻（2026-10-07 `?retro` 的教训），只做到单帧像、拼起来不连贯的也会（同日十段碎片演示的教训）。样片要是连续的一段音乐、带转场，不是几个镜头的碎片
- 参考片的原声：`python tools/grid_song.py 参考.mp4 --bpm <作者公布的速度> -o refs/<名>` 建一个歌曲目录（`refs/` 不进仓库），渲染加 `--song refs/<名>`、预览加 `?song=refs/<名>` 就配原声、按原片的拍子跑

## 3. 全片粗分镜

整首歌一次排完，**故意做粗**，让意见落在结构上，不落在质感上：

- 删掉示例场景 `app/src/scenes/demo*.ts` 和复刻场景 `ref_*.ts`（要抄的镜头先看完；基础引擎里一直留着），在 `app/src/timeline.ts` 按小节排场景（`audio.timeOfBar(k)`）；TREATMENT 的场景表、镜头表按小节写
- 每个场景先做占位：色块、简单几何、文字占位，但**运镜、切点、主体大小和位置、字幕出现的时机、能量的高低**都要是真的
- 渲染：`cd app && bun scripts/render.ts animatic` → `out/animatic/animatic.mp4`（30 fps、单采样、快速编码，左上角叠小节号「06/63」、镜头 id、段落、四拍方块，用户可以说“第 23 小节太碎”）。预览里打开 `/?animatic` 也有这个角标
- 自己先过一遍 `docs/质量验收.md` 第一节的 1、2、7 条（起伏、焦点、连着看连贯）和第三节“看片”的 0–4：先带音乐原速从头连着看一遍；`python tools/qa/seams.py out/animatic/animatic.mp4` 看每个切点前后的锚点、运动、亮度、色调（有参考片加 `--ref 参考.mp4`，列出参考有、我们没有的切点）；联系表 `render.ts sheet` 每 2 秒一帧，看景别、色调、密度有没有起伏，连着三个远景、整段一个构图就是问题
- 给用户看 animatic，**锁定**结构：每小节放什么、景别、节奏、转场方式

## 4. 关键镜头打样

- 挑 2–3 个最有代表性的镜头（最难的、最常出现的画风、签名镜头），做到成片质量
- 有目标图（Codex 概念图、用户给的参考）就用 `tools/compare.py` 并排对照（`docs/方法.md`）；有参考视频就用 `tools/refmatch.py`（`sheet` 同刻对照图、`video` 对照视频）
- **水准**：复古 / 故障 / 字符 / 像素这类效果，以基础引擎的 `?ref=<名>` 十段为下限（`docs/复刻配方.md` 第四节）；同类镜头先抄它们的结构和数值，再改成自己的
- 给用户看，**锁定**画面标准：之后“质感不够”“不高级”都拿这几帧对照着改，不再另立新标准

## 5. 分段精做

- 写场景前读 `docs/引擎指南.md`（确定性、线性 HDR、图层、后期参数、运动模糊）
- 一段一段把占位换成成片质量，**每段单独出短片**给用户看：`render.ts video --from a --to b --samples auto --max-samples 36`。意见只改这一段
- 静帧：`bun scripts/render.ts stills --t 12.5,13 --only 场景id`，渲完**亲眼看 PNG**
- 关键动作登记到场景的 `cues()`，用 `render.ts cues` + `tools/qa/cuecheck.py` 查卡点
- 中文字体只留用到的字：对齐完歌词（有中文译文时）、场景里加了或改了中文，跑一次 `python analysis/make_fonts_zh.py`，不然新字在 Canvas 文字里会落到系统字体，在轮廓 / 粒子字里缺字。开发中可加 `--gb2312` 留下全部常用字，加字不用重跑。`cd app && bun scripts/render.ts glyphs` 列出所有回落到系统字体的字（颜文字符号最常见），应为 0
- 有参考片的段：精做完按 `docs/复刻配方.md` 第五节验收三样（单帧像、连贯、运动量接近），再带音乐原速连着看

## 6. 整片合成、验收、发布

```bash
cd app && bun scripts/render-par.ts --samples auto --max-samples 36 --shutter 0.5 --out ../out/draft/v1.mp4
cd .. && python tools/qa/review.py out/draft/v1.mp4 --start <VIDEO_START>
python tools/qa/check_video.py out/draft/v1.mp4 --douyin out/qa/douyin_test.mp4   # 响度、音画偏移、3×3 闪光、空帧、色彩标签
python tools/qa/seams.py out/draft/v1.mp4 --start <VIDEO_START>                      # 每个切点的接缝
cd app && bun scripts/render.ts glyphs                                               # 缺字
```

先带音乐、原速、从头到尾连着看一遍成片，再看报告。

按 `docs/质量验收.md` 过一遍，决定写回 TREATMENT 的修订记录。到这一步应该只剩局部修。

- 抖音版：`python tools/douyin_mux.py <画面.mp4> audio/song.wav -o out/歌名_抖音版.mp4 [--audio-downbeat N]`
- 封面：`python tools/cover_title.py <4K 静帧> --line1 ... --line2 ...`
- `CREDITS`：引擎（MIT）、字体（OFL）、Codex 生成图、第三方代码、公共领域素材
- 发布前再跑一次 `tools/qa/check_video.py`（响度、闪光、BT.709 标签）
